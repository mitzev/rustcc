rustcc v1

Native C++ and Swift interop for Rust — no bindgen, no cxx shim crate, no build-script voodoo.

rustcc is a fork of rustc that teaches the compiler to emit Itanium-C++-ABI-compatible symbols and layouts for items tagged #[repr(cpp)], and Swift-ABI-compatible calls and metadata-driven witnesses for items tagged #[repr(swift)]. Rust code written in the fork links directly against Clang-compiled C++ and swiftc-compiled Swift modules — including virtual dispatch, constructors, destructors, single inheritance, dynamic_cast, ARC, and Swift value-witness tables.

Why this project exists

Rust has excellent FFI for C APIs. Everything else (C++ classes, Swift class / struct types, vtable dispatch across language boundaries) today requires a translation layer: cxx, bindgen + hand-written shims, autocxx, or custom build scripts. Every layer leaks incidental complexity: build steps, stubs, lifetime bookkeeping that doesn't match either language's native semantics.

rustcc's thesis is that the right place to handle this is the compiler itself, because the compiler already knows everything needed — type layout, calling conventions, symbol mangling, drop semantics. A modest set of targeted changes to rustc lets Rust programs speak C++ and Swift natively, without any intermediate representation or runtime shim.

If you've written impl Drop for Widget { fn drop(&mut self) { unsafe { cxx_widget_destroy(self); } } } before, this project is for you.

v2 roadmap

Not yet in v1, targeted for the next milestone:

  • Multi-inheritance and virtual bases — secondary vtable sub-tables, this-adjusting thunks, virtual-base offset slots.
  • True compiler auto-synthesis for #[repr(swift)] — today's path uses the swift_value! proc macro; a HIR-level trait-impl synthesis would let users drop the wrapper.
  • Multi-field class-backed Swift bindings with non-POD extra fields — e.g. a class handle that carries another class handle as a sibling field.
  • Const generics on class headers — class Array<T, const N: usize> { ... }. v1 accepts type and lifetime params only.
  • Windows MSVC ABI — out of scope for the Itanium-focused fork; would be a separate targeting effort.

Install the forked compiler

git clone <rustcc-repo> rustcc
cd rustcc/fork
./build.sh              # applies patches, builds stage-1 rustc
# ~30-90 min on a dev laptop

After the build, the toolchain lives at rust-lang-rust/build/host/stage1/bin/rustc. Either invoke it directly or register it with rustup:

rustup toolchain link rustcc /path/to/rust-lang-rust/build/host/stage1
rustup default rustcc

Quick start — "Hello from C++"

Three files: a C++ source, a Rust source, a C runner. Rust calls into C++.

hello.cpp

#include <cstdint>

extern "C++" {
    uint64_t cpp_double(uint64_t x) { return x * 2; }
}

probe.rs

#![crate_type = "staticlib"]

extern "C++" {
    fn cpp_double(x: u64) -> u64;
}

#[unsafe(no_mangle)]
pub extern "C" fn rust_entry() -> u64 {
    unsafe { cpp_double(21) }
}

runner.c

#include <stdio.h>
#include <stdint.h>
extern uint64_t rust_entry(void);
int main(void) { return (int)rust_entry(); }

Build & run

rustc probe.rs                        # emits libprobe.a with _Z9cpp_doubley referenced
clang++ -c hello.cpp -o hello.o
clang   -c runner.c -o runner.o
clang++ runner.o hello.o libprobe.a -o demo
./demo; echo $?                        # prints 42

No bindgen, no manual mangling — the Rust-side extern "C++" block produces the exact Itanium symbol Clang emits on the C++ side.

Example gallery

Five short end-to-end examples covering the v1 features. Detailed docs for each feature are in the Feature reference below.

1. A polymorphic class defined in Rust, called from C++

Rust declares a class with a virtual method and a constructor. The fork's compiler emits the Itanium vtable, typeinfo, and auto-initializes the vptr. C++ sees a Rust-defined type indistinguishable from one written in C++.

// widget.rs
#![feature(rustc_attrs)]

pub class Widget {
    v: i32,

    #[constructor]
    pub fn new(v: i32) -> Self { Widget { v } }

    #[cpp_virtual]
    pub fn foo(&self) -> i32 { self.v + 100 }
}

#[unsafe(no_mangle)]
pub extern "C" fn make_widget(v: i32) -> *mut Widget {
    Box::into_raw(Box::new(Widget::new(v)))
}

// caller.cpp
struct Widget {
    virtual int32_t foo();
    int32_t v;
};

extern "C" Widget* make_widget(int32_t v);

int main(void) {
    Widget* w = make_widget(7);
    return w->foo();   // dispatches into Rust's `foo` — returns 107
}

2. Single inheritance and dynamic_cast

Derived classes embed the base subobject at offset 0. The compiler emits an __si_class_type_info chain so dynamic_cast works across the boundary.

pub class Animal {
    name_len: u32,
    #[constructor] pub fn new(n: u32) -> Self { Animal { name_len: n } }
    #[cpp_virtual] pub fn legs(&self) -> u32 { 4 }
}

pub class Dog : Animal {
    volume: u32,
    #[constructor]
    pub fn new(n: u32, v: u32) -> Self {
        Dog { __base: Animal::new(n), volume: v }
    }
    #[cpp_virtual] pub fn bark(&self) -> u32 { self.volume * 10 }
}

// caller.cpp
Dog* d = make_dog(7, 3);
Animal* a = static_cast<Animal*>(d);      // upcast
a->legs();                                 // dispatches to Animal::legs via Dog's vtable
dynamic_cast<Dog*>(a);                     // recovers Dog* — libc++abi walks the chain

3. C++ constructor + destructor written in Rust

Tag the constructor with #[constructor] and the destructor via a regular impl Drop. The compiler emits Itanium _ZN<class>C1E<args> and D0/D1/D2 symbols — byte-identical to Clang.

#[repr(cpp)]
pub struct Texture { handle: u64 }

impl Texture {
    #[constructor]
    pub fn new(h: u64) -> Self { Texture { handle: h } }
}

impl Drop for Texture {
    fn drop(&mut self) {
        // C++ callers see this as `~Texture()`
        println!("freeing texture {}", self.handle);
    }
}

4. Calling a Swift class from Rust

The swift_value! macro auto-generates impl Drop and impl Clone with the right retain/release semantics.

rustcc_macros::swift_value! {
    #[swift_type = "MyLib.Counter:class"]
    pub struct Counter { pub handle: *mut core::ffi::c_void }
}

unsafe extern "Swift" {
    #[swift_symbol = "MyLib"]
    fn make_counter() -> Counter;
}

// Usage — Drop releases, Clone retains, everything native.
let a = unsafe { make_counter() };
let b = a.clone();              // retains
drop(b);                        // releases
drop(a);                        // releases — Swift deinit fires

5. Cross-crate polymorphism

A polymorphic class defined in one crate is fully usable from another — the compiler-emitted attributes flow across crate boundaries so call-site mangling matches the definer's.

// crate_a/src/lib.rs
pub class Widget {
    v: i32,
    #[constructor]   pub fn new(v: i32) -> Self { Widget { v } }
    #[cpp_virtual] pub fn foo(&self) -> i32 { self.v + 100 }
}

// crate_b/src/lib.rs
use crate_a::Widget;

#[unsafe(no_mangle)]
pub extern "C" fn make_widget(v: i32) -> *mut Widget {
    Box::into_raw(Box::new(Widget::new(v)))
}

Feature reference

1. #[repr(cpp)] structs

Tag a Rust struct to opt into Itanium layout rules. The layout matches what Clang computes for a C++ class with the same field sequence, so records pass fields at the same offsets as C++ expects.

#[repr(cpp)]
pub struct Widget {
    pub handle: u64,
    pub count: u32,
}

Differences from #[repr(C)]: empty structs have size ≥ 1 (so distinct instances have distinct addresses, matching C++); empty structs with alignas(N) get size N (preserving the size % align == 0 invariant).

2. Free-function extern blocks

extern "C++" {
    fn cpp_add(a: i32, b: i32) -> i32;
    fn cpp_process(p: *const u8, len: u64) -> bool;
}

Scope nesting: if the extern "C++" block lives inside a mod, the Rust module path mirrors into C++ namespaces:

pub mod gfx {
    extern "C++" {
        pub fn render(x: i32) -> i32;   // mangles as _ZN3gfx6renderEi
    }
}

C++ side: namespace gfx { int32_t render(int32_t x); }.

3. Methods on #[repr(cpp)] types

Any method declared in an impl block on a #[repr(cpp)] type automatically gets the Itanium member-function calling convention and mangling. No extern "C++" ABI annotation needed.

#[repr(cpp)]
pub struct Widget { pub handle: u64 }

impl Widget {
    pub fn area(&self) -> u64 {           // _ZNK6Widget4areaEv  (const-this)
        self.handle * 2
    }
    pub fn bump(&mut self, by: u64) {      // _ZN6Widget4bumpEy   (non-const-this)
        self.handle += by;
    }
}

C++ side:

struct Widget {
    uint64_t handle;
    uint64_t area() const;
    void bump(uint64_t by);
};
// Methods defined on the Rust side — C++ just declares and calls.
Note: methods are auto-exported with external linkage. The #[unsafe(no_mangle)] annotation is not required.

4. Constructors

Mark a method with #[constructor] to emit it as the C++ C1 complete-object constructor. Two directions work:

Rust implements the ctor (C++ callers link against Rust):

#![feature(rustc_attrs)]

impl Widget {
    #[constructor]
    pub fn new(h: u64) -> Self {            // _ZN6WidgetC1Ey
        Widget { handle: h }
    }
}

C++ implements the ctor (Rust callers link against C++) — since P09.22:

#![feature(rustc_attrs)]

unsafe extern "C++" {
    #[constructor]
    pub fn new(h: u64) -> Widget;           // _ZN6WidgetC1Ey
}

// usage: let w = unsafe { new(42) };

The compiler reads the class name off the return type (must be a #[repr(cpp)] ADT) and emits the Itanium _ZN<class>C1E<args> symbol — byte-identical to Clang. No #[link_name] needed.

5. Destructors

Implementing Drop on a #[repr(cpp)] type automatically emits the D1 complete-object destructor:

impl Drop for Widget {                       // _ZN6WidgetD1Ev
    fn drop(&mut self) {
        // runs on C++ scope exit, `delete`, or Rust scope exit
    }
}

No attribute needed — the destructor association is inferred from the Drop trait impl.

6. Passing records by value

A #[repr(cpp)] struct with Drop or !Copy is "non-trivial for calls" per Itanium: passed and returned by invisible reference (sret on return, ptr on args), regardless of size. Trivial POD-like types pass in registers.

#[repr(cpp)]
#[derive(Copy, Clone)]
pub struct Point { pub x: f32, pub y: f32 }    // trivial → passed in xmm registers

#[repr(cpp)]
pub struct Handle { pub raw: u64 }              // !Copy → passed indirectly

7. References in signatures

impl Widget {
    pub fn combine(&self, other: &Widget) -> u64 {   // _ZNK6Widget7combineERKS_
        self.handle + other.handle
    }
}

Rust &T maps to C++ const T&, &mut T to T&. Itanium type-substitution (S_, S0_, ...) is applied where appropriate.

8. Arrays

impl Widget {
    pub fn checksum(&self, counts: &[u64; 4]) -> u64 {
        // _ZNK6Widget8checksumERA4_Ky
        counts.iter().sum::<u64>() + self.handle
    }
}

C++ side: uint64_t checksum(const uint64_t (&counts)[4]) const.

9. C-like enums

#[repr(cpp, i32)]
pub enum Color {
    Red   = 1,
    Green = 2,
    Blue  = 4,
}

extern "C++" {
    fn paint(c: Color) -> u32;              // _Z5paint5Color
}

Equivalent C++: enum class Color : int32_t { Red = 1, Green = 2, Blue = 4 }; plus uint32_t paint(Color c);.

Restrictions (enforced at compile time):

  • An integer repr hint is required (i8/i16/i32/i64/i128 or unsigned counterpart). #[repr(cpp)] enum alone is rejected.
  • No data-carrying variants — C++ enum class has no tagged-union form.

10. C++ operator overloading

Mark a method with #[operator = "Kind"] to emit it with the C++ operator mangling. Supported:

impl Point {
    #[operator = "Plus"]
    pub fn op_add(&self, other: &Point) -> Point { ... }
    #[operator = "Eq"]
    pub fn op_eq(&self, other: &Point) -> bool { ... }
    #[operator = "Lt"]
    pub fn op_lt(&self, other: &Point) -> bool { ... }
    #[operator = "Index"]
    pub fn op_index(&self, i: u32) -> i32 { ... }
}

Emits _ZNK5PointplERKS_, _ZNK5PointeqERKS_, _ZNK5PointltERKS_, _ZNK5PointixEj — byte-identical to Clang's output for the equivalent C++ operator+, operator==, operator<, operator[].

Kinds: Plus, Minus, Mul, Div, Mod, Eq, Ne, Lt, Le, Gt, Ge, Assign, PlusAssign, Index, Deref, Call, PreIncr, PreDecr.

11. Swift extern "Swift" interop

Declare Swift module + type bindings via #[swift_symbol] / #[swift_type] on #[repr(swift)] struct bodies:

#[repr(swift)]
#[swift_type = "MyLib.Point"]
pub struct Point { pub x: f32, pub y: f32 }

unsafe extern "Swift" {
    #[swift_symbol = "MyLib"]
    fn magnitude(p: Point) -> f32;
}

Rust's side uses swiftcc calling convention for extern "Swift" items and spreads POD struct args field-by-field to match swiftc's ABI.

Swift classes (reference types) — add :class suffix:

#[repr(swift)]
#[swift_type = "MyLib.Counter:class"]
pub struct Counter { __ptr: *mut core::ffi::c_void }

impl Drop for Counter {
    fn drop(&mut self) {
        if !self.__ptr.is_null() {
            unsafe { rustcc_swift_rt::swift_release(self.__ptr); }
        }
    }
}

Swift's ARC is bridged via swift_retain / swift_release declared in the rustcc_swift_rt helper crate.

12. native_cpp_class! macro (fork-only)

For projects that want the ergonomic class Widget { ... } syntax without parser-level support, rustcc_macros::native_cpp_class! (added in P09.22) rides the compiler's unified #[constructor] path so declarations are minimal:

use rustcc_macros::native_cpp_class;

native_cpp_class! {
    #[size = 16] #[align = 8]
    pub class Texture {
        #[ctor] fn new(w: u64, h: u64) -> Self;
        fn area(&self) -> u64;
        fn scale(&mut self, by: u64);
    }
}

// usage:
let t = Texture::new(4, 5);          // _ZN7TextureC1Eyy
let a = t.area();                     // _ZNK7Texture4areaEv

Differences vs the stable-rustc-compatible cxx_class!:

  • Struct emits #[repr(cpp)], block emits extern "C++".
  • Ctors use #[constructor] — no sret trampoline, no hand-mangled #[link_name].
  • Inherent method wrappers carry #[rustc_cxx_wrapper] so P09.3 doesn't auto-export them (they'd otherwise collide with the C++ side's definition).
  • Auto-generated impl Drop that forwards to the C++ destructor (_ZN<class>D1Ev). Added in P09.23 via the new #[rustc_cxx_drop_wrapper] attribute — the trait-impl analogue of #[rustc_cxx_wrapper]. It opts Drop::drop out of P09.15's D0/D1/D2 auto-export so the C++ side is the sole definer and the Rust body just forwards. Users no longer need ManuallyDrop.

Because the expansion uses fork-only features, this macro only compiles under the rustcc stage-1 compiler. Stable-rustc users stay on cxx_class!.

13. Rust-defined polymorphic classes (fork-only, P09.24 + P09.25)

Rust can define a C++ class with virtual methods and have C++ callers dispatch through the vtable — Rust is the sole definer of _ZTV<class>, _ZTI<class>, and _ZTS<class>. Scope: single-inheritance, Itanium ABI, v1.

As of P09.25 no boilerplate is required. Just tag the virtual methods and write an ordinary ctor:

#![feature(rustc_attrs)]

#[repr(cpp)]
pub struct Widget { pub v: i32 }

impl Widget {
    #[constructor]
    pub fn new(v: i32) -> Self { Widget { v } }

    #[cpp_virtual]
    pub fn foo(&self) -> i32 { self.v + 100 }

    #[cpp_virtual]
    pub fn bar(&self) -> i32 { self.v * 2 }
}

What the compiler does under the hood:

  • Layout: reserves ptr_bytes at offset 0 for the vptr. User fields shift behind it. The struct's reported size includes the vptr slot.
  • Vtable / RTTI: emits _ZTV<class>, _ZTI<class>, _ZTS<class> as linkonce_odr constants.
  • Ctor vptr init: stores &_ZTV<class>[2] (the address point) into offset 0 at the start of every #[constructor] method, before user MIR runs.

C++ side declares the class layout and virtual signatures; the definitions come from the Rust side via Itanium mangling:

struct Widget {
    virtual int32_t foo();
    virtual int32_t bar();
    int32_t v;
};

extern "C" Widget* make_widget(int32_t v);  // Rust-defined

C++ calls like w->foo() load w->vptr, index slot 0 of the address-point view, and dispatch into Rust's foo.

v1 rules. (1) Single inheritance supported; multi-inheritance / virtual bases are v2 work. (2) Virtual method order = sort by (impl DefId, method DefId); user must keep the C++ header's virtual declaration order in sync. (3) Derived class may add new virtuals (go into vtable slots after base's) and may override a base virtual by declaring a derived virtual with the same method name (P09.34; matched by name only — mismatched signatures are user error). (4) dynamic_cast across inheritance works via libc++abi's runtime typeinfo chain walk. (5) Non-generic methods only.

15. Single inheritance — class Derived : Base

The fork's class keyword (see §14) accepts a C++-style inheritance clause. The parser synthesizes a first field __base: Base marked #[rustc_cxx_base]. Layout places the base subobject at offset 0 (so its vptr is also Derived's vptr slot), the vtable emitter combines base's virtual slots with derived's new virtuals, and the typeinfo chain uses __si_class_type_info so dynamic_cast walks the inheritance chain.

pub class Animal {
    name_len: u32,
    #[constructor] pub fn new(n: u32) -> Self { Animal { name_len: n } }
    #[cpp_virtual] pub fn legs(&self) -> u32 { 4 }
}

pub class Dog : Animal {
    volume: u32,

    #[constructor]
    pub fn new(n: u32, v: u32) -> Self {
        // User writes base init explicitly; compiler rewrites
        // the base's vptr to point at Derived's vtable at
        // return, so `static_cast(dog)->legs()` still
        // dispatches correctly.
        Dog { __base: Animal::new(n), volume: v }
    }

    #[cpp_virtual] pub fn bark(&self) -> u32 { self.volume * 10 }
}

C++ side mirrors the inheritance:

struct Animal {
    virtual uint32_t legs();
    uint32_t name_len;
};

struct Dog : Animal {
    virtual uint32_t bark();
    uint32_t volume;
};

extern "C" Dog* make_dog(uint32_t n, uint32_t v);

Calls through Dog* dispatch to both base and derived virtuals; upcasts to Animal* preserve dispatch; dynamic_cast<Dog*>(animal_ptr) recovers the derived pointer when the runtime type is Dog and returns nullptr otherwise.

v1 restrictions on inheritance. (1) Single inheritance only (multi-inheritance / virtual bases are v2). (2) Override matches by method name only — a derived virtual with the same name as a base virtual replaces the base's vtable slot, but a derived method whose signature doesn't match what C++ callers expect through the base pointer is user error (no lint for this in v1). (3) The __base field is synthesized by the parser; users reference it by name in struct literals but shouldn't redeclare it.

14. class keyword (fork-only, P09.30)

As of P09.30 the fork accepts the class keyword at item position. It parses identically to a #[repr(cpp)] struct plus an inherent impl, so everything downstream — §13's auto vptr slot, virtual dispatch, ctor mangling — carries over. The keyword is purely syntactic sugar with no additional semantics.

Example:

#![feature(rustc_attrs)]

pub class Widget {
    v: i32,

    #[constructor]
    pub fn new(v: i32) -> Self { Widget { v } }

    #[cpp_virtual]
    pub fn foo(&self) -> i32 { self.v + 100 }
}

is parsed as if the user had written:

#[repr(cpp)]
pub struct Widget { v: i32 }

impl Widget {
    #[constructor]
    pub fn new(v: i32) -> Self { Widget { v } }

    #[cpp_virtual]
    pub fn foo(&self) -> i32 { self.v + 100 }
}
v1 rules. (1) Fields must come before methods inside the class body. (2) Fields don't support outer attributes — anything starting with # is parsed as a method. (3) class is a weak keyword, so let class = 5; still parses as a normal binding. (4) No generics on the class header in v1. (5) The fork-specific compiler attributes (#[constructor], #[cpp_virtual]) still apply on methods inside a class — they aren't auto-inferred from context.

16. Bare-metal / STM32 / Raspberry Pi Pico targets (fork, P09.36 / P09.38)

The fork compiles cleanly for bare-metal 32-bit ARM targets from the ARMv6-M family up through ARMv8-M — covering STM32 parts, Raspberry Pi Pico / Pico W (RP2040 Cortex-M0+, thumbv6m-none-eabi; P09.38), and Pico 2 in Cortex-M33 mode (thumbv8m.main-none-eabihf). The existing Itanium-ABI machinery is target-aware enough that no ABI-specific compiler changes are needed for ARM Cortex-M; the only link-time knob is providing a stub for libc++abi's RTTI vtable since bare-metal builds typically don't link libc++abi.

Minimal probe (see /tmp/p09-39-arm32/):

// src/lib.rs
#![no_std]
#![feature(rustc_attrs)]

pub class Widget {
    v: i32,
    #[constructor]  pub fn new(v: i32) -> Self { Widget { v } }
    #[cpp_virtual]  pub fn foo(&self) -> i32 { self.v + 100 }
}

// Bare-metal boilerplate
#[panic_handler]
fn panic(_: &core::panic::PanicInfo) -> ! { loop {} }

Build — use a nightly cargo as the driver (so -Zbuild-std is accepted), but override RUSTC to point at the fork's stage-1:

RUSTC=/path/to/rust-lang-rust/build/host/stage1/bin/rustc \
RUSTC_BOOTSTRAP=1 \
cargo +nightly build --target thumbv7em-none-eabihf \
  -Zbuild-std=core,compiler_builtins

The output under target/thumbv7em-none-eabihf/debug/ contains correctly-mangled Itanium symbols with 32-bit pointer widths throughout:

  • _ZN6WidgetC1Ei — ctor, sret-style (void return with hidden this arg). Matches arm-none-eabi-g++'s expectations for thumbv7em.
  • _ZNK6Widget3fooEv — const-this virtual.
  • _ZTV6Widget — vtable of shape { i32, ptr, ptr }: 4-byte offset-to-top, 4-byte typeinfo pointer, 4-byte fn pointer.
  • _ZTI6Widget / _ZTS6Widget — typeinfo and typeinfo-name.

Link-time stub for the libc++abi RTTI vtable:

// rtti_stub.c — 3 lines satisfy the only external reference.
__attribute__((weak))
void* _ZTVN10__cxxabiv117__class_type_infoE[4] = { 0 };

Compile with arm-none-eabi-gcc -mcpu=cortex-m4 -mthumb. This stub is enough for virtual dispatch to work at runtime — the typeinfo pointer in the vtable exists so the linker is happy, but dynamic_cast and typeid won't do anything meaningful without real libc++abi. Users who want full RTTI can link against libsupc++-nano (shipped with arm-none-eabi-gcc) or an equivalent instead of the stub.

End-to-end partial link:

arm-none-eabi-g++ -mcpu=cortex-m4 -mfpu=fpv4-sp-d16 \
  -mfloat-abi=hard -mthumb -c caller.cpp -o caller.o -std=c++17

arm-none-eabi-gcc -mcpu=cortex-m4 -mfpu=fpv4-sp-d16 \
  -mfloat-abi=hard -mthumb -c rtti_stub.c -o rtti_stub.o

arm-none-eabi-ld -r caller.o rtti_stub.o \
  --whole-archive libp09_39_arm32.a -o probe.o
# probe.o: ELF 32-bit LSB relocatable, ARM, EABI5 version 1
# All symbols resolved, no undefined references.
Other ARM Cortex-M targets (all validated by probe). thumbv6m-none-eabi (Cortex-M0+ — Raspberry Pi Pico / Pico W; P09.38), thumbv7m-none-eabi (Cortex-M3), thumbv8m.base-none-eabi (M23), thumbv8m.main-none-eabihf (M33F — Pico 2 in ARM mode), etc. all emit identical Itanium output to thumbv7em-none-eabihf — same ctor sret+void shape, same 4-byte vtable slots, same address-point offset 8. If a specific triple produces different mangling vs arm-none-eabi-g++, open an issue with the ABI fact that mismatches.

17. ESP32 (RISC-V) / bare-metal rv32 (fork, P09.37)

RISC-V-based ESP32 parts (ESP32-C3 / C6 / H2 / P4) and any bare-metal rv32 / rv64 ELF target are supported. Unlike ARM Cortex-M, this did need a small compiler patch: upstream's rv32 calling convention ICEd on polymorphic #[repr(cpp)] layouts because the fp-conv probe doesn't expect the vptr slot at offset 0. P09.37 adds an Itanium overlay for rv32 / rv64 mirroring the x86_64 and aarch64 ones — polymorphic and other non-trivial-for-calls types are passed by invisible reference, matching what Clang and GCC emit per the RISC-V psABI.

Supported triples:

  • riscv32imc-unknown-none-elf — ESP32-C3 (validated probe: /tmp/p09-40-riscv32-esp32c3/).
  • riscv32imac-unknown-none-elf — ESP32-C6 / H2.
  • riscv32imafc-unknown-none-elf — ESP32-P4.
  • riscv32imc-esp-espidf / riscv32imac-esp-espidf / riscv32imafc-esp-espidf — ESP-IDF std targets.
  • Any other rv32 / rv64 ELF Itanium-ABI target.

Build recipe is identical to the ARM Cortex-M flow, just with a different --target:

RUSTC=/path/to/rust-lang-rust/build/host/stage1/bin/rustc \
RUSTC_BOOTSTRAP=1 \
cargo +nightly build --target riscv32imc-unknown-none-elf \
  -Zbuild-std=core,compiler_builtins

The validated polymorphic Widget emits:

  • void @_ZN6WidgetC1Ei(ptr sret([8 x i8]) %_0, i32 %v) — ctor signature matches Clang's Itanium output for Widget::Widget(int) on rv32.
  • { i32, ptr, ptr } vtable with 4-byte slots, address-point offset 8.
  • Correct Itanium mangling: _ZN6WidgetC1Ei, _ZNK6Widget3fooEv, _ZTV6Widget, _ZTI6Widget, _ZTS6Widget.

The same libc++abi RTTI stub from §16 applies if you're not linking a real C++ runtime:

// rtti_stub.c
__attribute__((weak))
void* _ZTVN10__cxxabiv117__class_type_infoE[4] = { 0 };

Compile the C++ side with riscv32-esp-elf-g++ (ESP-IDF toolchain) or riscv32-unknown-elf-g++ (generic RISC-V GCC) or Espressif's Clang/LLVM RISC-V toolchain — all three use the same Itanium C++ ABI, so the Rust side's symbols and calling convention are compatible with any of them.

Xtensa ESP32 (S3 / original ESP32) is not supported. Xtensa has no upstream rustc target; Espressif maintains their own LLVM / Rust forks for Xtensa but those are out of scope for this fork. Only RISC-V-based ESP32 parts (C3, C6, H2, P4) run Rust today.

Minimum working end-to-end example

A full round trip: C++ defines a class, Rust implements methods on it, C++ uses those methods.

widget.hpp (C++ declares the class shape)

#pragma once
#include <cstdint>
struct Widget {
    uint64_t handle;
    Widget(uint64_t h);
    ~Widget();
    uint64_t area() const;
};

widget.rs (Rust provides the implementation)

#![crate_type = "staticlib"]
#![feature(rustc_attrs)]

#[repr(cpp)]
pub struct Widget { pub handle: u64 }

impl Widget {
    #[constructor]
    pub fn new(h: u64) -> Self { Widget { handle: h } }

    pub fn area(&self) -> u64 { self.handle * 2 }
}

impl Drop for Widget {
    fn drop(&mut self) { /* D1 runs on scope exit */ }
}

main.cpp (C++ uses the class)

#include "widget.hpp"
#include <cstdio>

int main() {
    Widget w(21);
    std::printf("area = %llu\n", (unsigned long long)w.area());
    return 0;
}

Build

rustc widget.rs
clang++ -c main.cpp -o main.o
clang++ main.o libwidget.a -o demo
./demo                  # prints: area = 42

Three symbols resolve at link time: _ZN6WidgetC1Ey (ctor), _ZNK6Widget4areaEv (method), _ZN6WidgetD1Ev (dtor) — all from the Rust staticlib.

Troubleshooting

"undefined symbol _ZN6Widget..." at link time

The C++ side references a symbol the Rust side didn't define (or vice versa). Check:

  • Method signatures match on both sides (including const vs non-const).
  • The Rust impl method is defined with a body (declarations without bodies don't emit a symbol).
  • Namespace nesting matches between Rust mod hierarchy and C++ namespace hierarchy.

Inspect what Rust emitted:

nm libwidget.a | grep -i widget
# or: rustc --emit=llvm-ir widget.rs && grep -E "^define" widget.ll

Inspect what C++ expects:

clang++ -S -emit-llvm main.cpp -o main.ll && grep '@_Z' main.ll | head

"type X cannot appear in an extern "C++" signature"

The Rust→C++ type mapper doesn't know how to mangle X. The error points at the fn item that's involved. Common cases:

  • &str / slices / tuples → pass as *const u8 + u64 or a #[repr(cpp)] struct.
  • isize / usize → use explicit i64 / u64.
  • Non-repr(cpp) Rust structs in a C++ signature → either add #[repr(cpp)] to the struct or pass as a pointer.

"#[repr(cpp)] enum requires an explicit integer repr hint"

Add one: #[repr(cpp, i32)].

"#[repr(cpp)] enum cannot have variants with data"

C++ enum class has no tagged-union form. If you need variants with payload, use a #[repr(cpp)] struct + discriminant manually, or declare a C++ union.

ABI mismatch between Rust and C++ calls

For records, check triviality:

  • Rust side has impl Drop or is !Copy → passed indirectly.
  • C++ side has a user-declared destructor, copy ctor, or move ctor → Clang also passes indirectly. Consistent.

If the C++ class is trivial but the Rust type isn't (or vice versa), the ABIs diverge. Make both sides trivial (Rust: #[derive(Copy, Clone)], no Drop) or both non-trivial.
